# SALON STATION — 利用者ストアと運営管理画面

[利用者サイト](https://acuerdo-sr.github.io/salon-station-demo/) ／ [管理画面](https://acuerdo-sr.github.io/salon-station-demo/admin.html) ／ [ソース](https://github.com/acuerdo-sr/salon-station-demo)

美容室を販売主体とし、消費者の注文からディーラー別の発注を作成し、ディーラーが消費者へ直送するECの試作です。EC-CUBE・外部CRMは使用していません。商品、店舗、顧客、決済、発送はすべて架空のデモです。

## 5分で試す

1. 利用者サイトは会員限定（クローズド）です。「ログインする」→「架空のデモ会員を作成して体験する」を押すと商品一覧が開きます。カテゴリー・お悩み別で商品を探し、カートに追加します。
2. 架空のお届け先で注文すると、販売サロンの受注とディーラー別の発注が作成されます。
3. 同じブラウザの別タブで管理画面を開き、「管理会社」を選んでデモログインします。
4. 「ディーラー発注」で該当発注を受注し、配送会社・架空の追跡番号を入力して出荷します。
5. 利用者サイトの購入履歴を開くと、配送状況と追跡番号が反映されます。

加盟店（サロン）から本部への発注は、`order.html`（加盟店の発注画面）で試せます。スマートフォンとLINEから開く前提の画面です。

1. 発注画面を開き、加盟店アカウントでログインします。公開版は「LINEで発注を始める（デモ）」でも入れます。
2. 「発注のご提案」の数量を追加するか、商品を選んで発注します。卸価格（税込）で、11,000円以上は送料無料です。
3. 「履歴」の「同じ内容で発注」で再注文できます。発注内容の確認画面から定期発注（毎週・2週間ごと・毎月）も登録できます。
4. 管理画面に「管理会社」でログインし、「加盟店発注」で受付と出荷を行います。「請求書」で前月分を締めると、加盟店ごとの請求書が発行されます。
5. 「店販の取り分」で、ECで売れたときと店頭で売ったときにサロンに残る金額を比べられます。

管理画面には初期サンプル注文8件があります。利用者が作成した注文も追加されます。更新は15秒ごと・画面に戻ったときに取得します。管理画面右上の更新ボタンでも取得できます。モーダル操作中は自動更新を止めます。

## 実装した機能

- 利用者：会員限定ストア（未ログインには商品・価格を表示しない）、商品検索（商品名・説明文）・カテゴリー・お悩み別検索・並べ替え、商品詳細、お気に入り、会員・サロン別カート、会員登録・ログイン（フリガナ・電話番号・性別・生年月日は任意）、LINEログイン・LINE登録・LINEアカウント連携、LINEミニアプリからの自動ログイン、サロン・担当スタッフの紐付け（QRの `?shop_id=` / `?salon=` 対応）、マイページ、注文、購入履歴、配送状況。
- 管理会社：加盟店発注の受付・出荷、定期発注の確認と即時実行、月末締めと請求書の発行・入金管理、卸価格の設定、売上・対応件数ダッシュボード、売上集計（日次・月次・年次・任意期間 × 全店舗・店舗別、販売金額・受注件数・顧客数、CSV出力）、店舗横断の受注・ディーラー発注、商品価格・仕入原価・在庫・公開設定、店舗の登録・編集・削除（住所・電話番号・営業時間・定休日・備考・スタッフ・運用料率・受付設定）、会員一覧・担当店舗紐付けの変更、精算見込、操作履歴。
- 加盟店（美容室）からの発注：スマートフォン・LINE向けの発注画面、卸価格での発注、発注提案（いつもの発注間隔から必要な商品と数量を提案）、前回と同じ内容での再注文、定期発注（毎週・2週間ごと・毎月、期日に自動作成）、月末締めの請求書（加盟店ごとに1か月分をまとめ、適格請求書の記載事項を含む。印刷・PDF・CSV）、発注受付・出荷・定期発注作成のLINE通知、店販の取り分の比較（EC直送と店頭販売で1点あたり・本数あたりにサロンに残る金額）。
- 美容室：自店舗の受注・会員・売上集計・精算、自店舗情報（店舗名・住所・電話番号・営業時間・定休日）の編集、サロン紹介リンク・QRコード（PNG 600×600px・誤り訂正レベルM）。
- ディーラー：自社の発注受注、出荷・追跡番号・配達完了、在庫変更。
- 注文処理：価格・在庫の再確認、重複送信防止、在庫減算、仕入先ごとの発注分割、分割出荷、出荷前キャンセル、全商品の出荷後の返品申請と管理会社の検品・返金処理。

送料は注文1件につき660円、商品合計11,000円以上で無料。分割出荷による追加送料はありません。注文時の価格・仕入原価・運用料率・販売店・担当者を記録し、後の変更で過去の注文を変えません。返品は注文全体を対象にし、部分返品・交換は対象外です。

精算は、商品売上 − 仕入原価 − 商品売上に対する運用料金の試算です。送料をディーラーへの支払見込に配賦します。無料配送時の実運賃、決済手数料、保管料、税務仕訳等を含む本番の利益計算・送金機能ではありません。

## 公開版とローカル版の違い

| 項目 | GitHub Pages | ローカル版 |
|---|---|---|
| データ保存 | 閲覧者のブラウザ | データベース（既定は SQLite、`DATABASE_URL` で MySQL 8.0） |
| 画面間の共有 | 同じブラウザ・同じサイト内のみ | 同じローカルサーバーに接続したブラウザ間 |
| 管理者認証 | ブラウザ内の体験用 | サーバーのセッション照合と役割判定 |
| 利用者認証 | ブラウザ内の体験用 | サーバーの会員セッション照合 |
| 決済・自動発注・返金・発送 | シミュレーション | シミュレーション |

公開版は、別端末や別ブラウザで開くと独立したデータになります。管理者を切り替えると表示範囲も変わりますが、ブラウザに全デモデータがあるため本番のアクセス制御にはなりません。公開版の会員と管理者セッションはタブ単位です。公開版を初期化する場合は、このサイトのブラウザ保存データを削除します。

ローカル版は会員パスワードをsalt付きPBKDF2-HMAC-SHA-256で処理し、CookieはHttpOnly・SameSite=Strict。サーバーで管理会社・美容室・ディーラーの範囲を確認します。管理アカウントは公開されたデモ認証情報のため、本番利用はできません。

## ローカルで起動

Node.js 22.13以降を使用します。このPCでは22.20.0で確認しました。

```powershell
npm ci
npm start
```

- 利用者： http://127.0.0.1:4175/
- 管理者： http://127.0.0.1:4175/admin.html

停止は起動したターミナルでCtrl+C。`start.ps1` はバックグラウンド起動、`stop.ps1` は同スクリプトで記録したサーバーのみ停止します。従来の4173ポートの試作とは起動先を分けています。

画面は `dist/shop.html` と `dist/admin.html` です。サーバーはルートURLと `/index.html` を `shop.html` に割り当てます。会員限定ストアを迂回して価格を返していた旧画面と旧API（`/api/products`・`/api/quote`・`/api/orders`）は削除しました。データの保存先は下の「データベース」を参照してください。

担当サロンは、QRコードまたは会員登録時の最初の紐付けで決まります。会員が自分で変更できるのは担当スタッフだけで、担当サロンの変更は管理画面の「担当店舗の紐付け変更」で行います。店舗IDは削除後も再利用しません。

カート・お気に入りは会員ごとにサーバーへ保存し、別の端末でも続きから買い物できます。前回のお届け先は次の注文画面に入力済みで表示します。サーバーは127.0.0.1に限定して待ち受けます。公開時は nginx などのリバースプロキシの裏で動かし、`PUBLIC_ORIGIN`・`TRUST_PROXY` を設定します。

## データベース

ローカル版・本番用のサーバーは、正規化したテーブルにデータを保存します。既定は SQLite（`data/shop.sqlite`）で、環境変数 `DATABASE_URL=mysql://ユーザー:パスワード@ホスト:3306/DB名` を設定すると MySQL 8.0 を使います。業務処理は同じで、SQL の違いは `db/adapter.mjs` で吸収しています。

| 領域 | テーブル | 役割 |
|---|---|---|
| 店舗 | `salons`, `staff`, `dealers` | 店舗マスタ（住所・電話・営業時間・運用料率・受付設定）、担当スタッフ、仕入先 |
| 商品 | `products`, `categories`, `concerns`, `product_concerns` | 商品（SKU・税込価格・仕入単価・加盟店への卸価格・税率・在庫・公開）、カテゴリ、お悩み |
| 会員 | `members`, `member_sessions`, `member_addresses` | 会員マスタ（担当店舗・担当スタッフ・LINE ID・同意した取り扱いの版と日時を含む）、ログイン、お届け先 |
| 管理者 | `operators`, `operator_sessions` | 本部・美容室・ディーラーのアカウント（パスワードはハッシュ、LINE ID）とログイン |
| 購入前 | `cart_items`, `favorites` | 会員ごとのカートとお気に入り |
| 注文 | `orders`, `order_items`, `order_events` | 注文（注文時点の価格・店舗・担当者・お届け先・消費税額）、明細、配送状況の履歴 |
| 発注・配送 | `purchase_orders` | ディーラー別の発注、配送会社、追跡番号 |
| 決済 | `payments`, `refunds` | 決済の状態と返金（カード情報は持たない） |
| 在庫 | `stock_movements` | 初期・注文・キャンセル・返品・手動調整による増減の履歴 |
| 加盟店発注 | `supply_orders`, `supply_order_items`, `supply_subscriptions`, `supply_subscription_items`, `invoices` | 加盟店からの仕入発注（卸価格・届け先を保存）、定期発注、月末締めの請求書 |
| 記録 | `audit_logs`, `notifications`, `counters`, `app_meta` | 操作履歴、LINE通知の送信記録（1件につき1回）、採番・更新番号、スキーマ版数 |

設計上の決まり：

- 注文と明細には、注文時点の価格・仕入単価・販売店舗・担当スタッフ・運用料率・お届け先を写して保存します。後の変更で過去の売上と精算は変わりません。
- 会員側の店舗は「現在の担当」、注文側の店舗は「売った店舗」です。売上集計と精算は注文側で行います。
- 金額は円の整数（税込）で、注文には含まれる消費税額（10%）を保存します。日時は UTC の ISO 形式で、売上集計用に日本時間の注文日（`ordered_on`）も保存します。
- 在庫は「足りる場合だけ減らす」条件付き更新で、注文と同じトランザクションの中で確保します。同時注文でも売り越しません。増減はすべて `stock_movements` に残ります。
- 注文識別子に一意制約があり、再送や二度押しで注文が増えません。店舗IDは `counters` で採番し、削除後も再利用しません。
- 注文が紐付いた店舗・商品は削除せず休止します。外したスタッフも削除せず無効にします。

起動時に、テーブルが無ければ作成し、空なら公開デモと同じサンプルデータを入れます。前の版で作ったDBには、卸価格と管理者のLINE IDの列、加盟店発注の表を自動で追加します。以前の版の `data/shop.sqlite`（全データを1行のJSONで保存していた形式）があれば、自動で新しいテーブルへ移行し、元の表は `legacy_` 付きの名前で残します。会員のパスワードとログイン状態もそのまま引き継ぎます。

MySQL で使う場合は、空のデータベースを作成して `DATABASE_URL` を設定し、`npm start` で起動します（テーブル作成と初期データ投入は自動）。MySQL での業務テストは `TEST_MYSQL_URL` を設定して `npm test` を実行すると、SQLite と同じ共通テストが MySQL でも走ります。このテストは空のデータベースを前提に表を作り直すため、本番DBには向けないでください。

## LINE連携の設定

LINEログイン（会員登録・ログイン・既存会員への連携）、LINEミニアプリ（LIFF）、注文受付・出荷のLINE通知に対応しています。ローカル版はチャネル情報が未設定だとLINEの導線を表示しません。公開版（GitHub Pages）はLINEと通信せず、「LINEでログイン（デモ）」で架空のLINE会員を作成して流れを体験します。

1. [LINE Developers](https://developers.line.biz/) でプロバイダーを作成し、「LINEログイン」チャネルを追加します。チャネルID・チャネルシークレットを控えます。
2. LINEのコールバックURLは https が必要です。ローカル検証では cloudflared や ngrok などのHTTPSトンネルでこのサーバーを公開し、そのURLを `PUBLIC_ORIGIN` に入れます。LINE Developers の「コールバックURL」には `PUBLIC_ORIGIN` + `/api/auth/line/callback` を登録します。
3. LINEミニアプリとして使う場合は、同じLINEログインチャネルに LIFF アプリを追加し、エンドポイントURLに `PUBLIC_ORIGIN` を設定して LIFF ID を控えます。
4. 通知も使う場合は「Messaging API」チャネルを作成し、長期チャネルアクセストークンを控えます。通知を受け取るには、会員がそのLINE公式アカウントを友だち追加している必要があります。
5. `.env.example` を `.env` にコピーして値を入れ、`npm start` で起動します（`.env` はGit管理外です）。

| 変数 | 内容 |
|---|---|
| `LINE_CHANNEL_ID` / `LINE_CHANNEL_SECRET` | LINEログインチャネル |
| `PUBLIC_ORIGIN` | 外部公開URL。コールバックURLとログイン後の戻り先に使用 |
| `LIFF_ID` | お客様向けストアの LIFF アプリの ID（任意）。設定すると LINE アプリ内で開いたときに自動ログイン |
| `LIFF_ID_ORDER` | 加盟店の発注画面の LIFF アプリの ID（任意）。エンドポイントURLは `PUBLIC_ORIGIN` + `/order.html`。一度メールでログインして「LINEと連携」すると、次回から LINE で開くだけでログイン |
| `LINE_MESSAGING_TOKEN` | Messaging API のアクセストークン（任意）。注文受付・出荷を通知 |
| `LINE_SCOPE` | 既定 `profile openid`。メールアドレス取得の権限を申請済みなら `profile openid email` |
| `ALLOWED_HOSTS` | 追加で許可するホスト（カンマ区切り） |
| `TRUST_PROXY` | トンネル・リバースプロキシ配下では `1`。ログイン試行制限で `X-Forwarded-For` の接続元IPを使う |

`PUBLIC_ORIGIN` が `https://` のときは、セッションCookieに `Secure` を付けます。ログイン試行の制限は「接続元IP × メールアドレス」単位で、1人の誤入力で他の利用者がロックされることはありません。

LINEログインの `state` は、開始したブラウザの Cookie（HttpOnly・SameSite=Lax・10分）にも保存し、コールバックで一致を確認します。別のブラウザで認可を完了させる手口（ログインCSRF・LINE連携の乗っ取り）は失敗します。ログイン失敗時は理由コード（`cancelled`・`expired`・`conflict`・`failed`）だけを返し、表示文言は画面側で固定しています。LINE通知は新規注文と出荷の時だけ送り、注文の再送や出荷操作の二度押しでは重複して送りません。

動作の流れ：店頭QR（`?shop_id=店舗ID`）→「LINEで登録」→ LINEの認可画面 → `/api/auth/line/callback` でIDトークンを検証し、LINEのユーザーIDで会員を特定します。未登録なら氏名をLINEのプロフィールから取り込み、QRの店舗・担当スタッフに紐付けて登録します（メールアドレスの権限がない場合は `line-…@example.test` の仮アドレス）。ログイン中の会員が操作した場合は、その会員にLINEを連携します。IDトークンの検証はLINEの検証エンドポイントで行い、`state` と `nonce` を照合します。

本番では、LINEの[ボタンデザインガイドライン](https://developers.line.biz/ja/docs/line-login/login-button/)に沿った公式ボタン画像の使用、メールアドレス取得の権限申請、通知メッセージの文面設計が必要です。

## 顧客データの取り扱い

お客様の情報は担当サロンのものとし、運営本部は集計値だけを扱います。ルールは `dist/privacy.js` にまとめ、ブラウザ版・DB版・画面で共有しています。

| 見る人 | 見られるお客様の情報 |
|---|---|
| 担当サロン | 自店のお客様の氏名・メール・電話・お届け先・購入履歴・会員番号 |
| 運営本部 | 店舗ごとの会員数・LINE連携数・今月の新規・購入者数・リピーター数・リピート率と、個人を特定しない会員番号だけ。受注・発注の画面ではお客様名の代わりに会員番号を表示し、お届け先は表示しない |
| ディーラー | 発送に必要なお名前・郵便番号・お届け先だけ。メールアドレスと会員の一覧は渡さない |
| お客様 | 自分の会員情報・購入履歴・会員番号 |

- **会員番号**：`M-` で始まる8桁の番号です。お客様のマイページと、サロンの会員一覧に表示します。担当店舗の付け替えは、本部がこの番号を入力して行います。
- **同意の記録**：会員登録の画面で「お客様情報の取り扱い」を表示し、同意を必須にしています。同意した版（`PRIVACY_VERSION`）と日時を会員ごとに保存します。LINEでの登録とデモ会員の作成は、画面上の案内のとおり同意したものとして記録します。
- **操作履歴**：お客様の操作は氏名ではなく会員番号で記録します。

本部の管理画面で個人情報を出さないのは画面と応答の制御で、DBには全項目が保存されています。DBを直接見られる担当者の範囲、アクセス記録、委託契約での取り決めは、本番運用の前に別途決める必要があります。

## 加盟店からの発注と請求

| 機能 | 内容 |
|---|---|
| 発注画面 | `order.html`。加盟店アカウント（美容室の役割）専用。商品ごとの卸価格・在庫を見て発注する |
| LINEで発注 | 発注画面を LINE ミニアプリとして登録すると、LINE のトークやリッチメニューから開ける。管理アカウントと LINE を一度連携すれば以後は自動ログイン |
| 発注提案 | 過去180日に2回以上発注した商品について、平均の発注間隔の8割が過ぎたら、前回と同じ数量を提案する |
| 再注文 | 履歴から前回と同じ内容をカートに入れる。在庫がない商品は除く |
| 定期発注 | 毎週・2週間ごと・毎月。期日になるとサーバーが10分ごとの確認で自動作成する（同じ期日の重複作成はしない）。在庫不足で作れなかった場合は結果を残して次回へ進める |
| 月末締め・請求書 | 本部が「請求書」で終わった月を締めると、キャンセル以外の発注を加盟店ごとに1通にまとめる。支払期限は翌月末。発行者の登録番号、税率、消費税額を記載し、印刷・PDF・CSVに対応 |
| 店販の取り分 | 商品ごとに、EC（直送・在庫なし）で売れたときの取り分（売価 − 仕入原価 − 運用料）と、店頭販売の取り分（売価 − 卸価格）を比べる。本数を入れると、店頭販売で先に必要な仕入代金も表示する |
| LINE通知 | 加盟店スタッフ（LINE連携済み）に、発注受付・出荷・定期発注の作成を通知する |

加盟店の発注は、ディーラー直送と同じ在庫から引き当てます。請求書の発行者名・登録番号・振込先は架空の値で、`dist/supply-core.js` の `ISSUER` で本番の値に置き換えます。デモの卸価格は売価の65%、仕入原価は60%で、運用料率5%のときECと店頭の1点あたりの取り分が同じになるように設定しています。実際の価格は管理画面の「商品・在庫」で設定してください。
